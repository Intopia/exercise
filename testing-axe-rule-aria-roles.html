Testing the axe rule aria-roles

Test cases for the axe-core rule aria-roles (axe-core 4.14). The rule checks that the role attribute uses a real role. It runs three checks, and fails if any of them finds a problem:

  • invalidrole: none of the roles in the attribute are real roles. If one of them is real, this check passes.
  • abstractrole: one of the roles is an abstract role. These exist to organise the ARIA spec, and authors mustn't use them.
  • unsupportedrole: the role isn't well supported. No roles are on that list in 4.14.

Role names aren't case sensitive, and an empty role attribute isn't tested. Deprecated roles, such as directory, are checked by a different rule, aria-deprecated-role.

Each case also shows the axe message key and which Intopia issue template the result would go to under the current assembly rules. Results on this page were checked in Chrome, including how Chrome exposes each role.

axe-core results: See the HTML report from running axe-core 4.14.0 over this page.

Every example is live in the page, so you can run the axe extension straight over it. The expected results were checked by running axe-core 4.14.1 over this page. Look in both the axe issues list and the needs review list.

Roles that don't exist

These fail with "Role must be one of the valid ARIA roles". Browsers fall back to the element's own role.

A1 A misspelled role

Continue
<div role="buton" tabindex="0">Continue</div>

Expected result: fail

In Chrome, this is exposed as a generic element.

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

A2 A misspelled role in capitals

Capitals don't matter, but the spelling is still wrong.

Next
<div role="BUTON" tabindex="0">Next</div>

Expected result: fail

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

A3 An HTML element name

nav is an HTML element, not a role. The role is navigation.

Home | Shop | Contact
<div role="nav">Home | Shop | Contact</div>

Expected result: fail

In Chrome, this is exposed as a generic element.

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

A4 A heading level in the role

Use role="heading" with aria-level.

Our story
<div role="heading1">Our story</div>

Expected result: fail

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

A5 presentational

The role is presentation.

Decorative box
<div role="presentational">Decorative box</div>

Expected result: fail

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

A6 Roles separated by a comma

A role list must be separated by spaces. With a comma, it's read as one role called button,link.

Menu
<div role="button,link" tabindex="0">Menu</div>

Expected result: fail

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

A7 role="generic"

generic is a real role in ARIA 1.2, and Chrome exposes it. But the spec says authors shouldn't use it, and axe treats it as invalid.

Wrapper
<div role="generic">Wrapper</div>

Expected result: fail

In Chrome, this is exposed as generic, so this fail is arguably a false positive. The fix is simply to remove the role.

Template routing: Check: invalidrole, message key: none. Routes to: NEW-30.

Accepted by axe, but worth knowing

These pass, but each has a catch.

C1 A role in capitals

Subscribe
<div role="Button" tabindex="0">Subscribe</div>

Expected result: pass (valid)

In Chrome, this is exposed as a button. Note that aria-command-name doesn't test it, because its selector only matches an exact role="button".

C2 A misspelled role, then a real one

invalidrole only fails when every role is invalid, so the typo is never reported.

Download
<div role="buton button" tabindex="0">Download</div>

Expected result: pass (valid)

In Chrome, this is exposed as a button, so it works.

C3 role="image"

image is a new name for img in the ARIA 1.3 draft.

***** 
<span role="image" aria-label="Five stars">*****</span>

Expected result: pass (valid)

In Chrome, this is exposed as an image. Older browsers and screen readers may not know it.

C4 role="text"

Not a WAI-ARIA role at all, but axe accepts it because Safari supports it.

Now $24.99 
<span role="text">Now <strong>$24.99</strong></span>

Expected result: pass (valid)

In Chrome, this is exposed as a generic element. Safari reads the content as one phrase.

C5 role="mark" and role="comment"

Both are in the ARIA 1.3 draft.

Our best seller is back.

Check this price.
<p>Our <span role="mark">best seller</span> is back.</p>
<div role="comment">Check this price.</div>

Expected result: pass (valid)

Chrome exposes both. Support in screen readers varies.

Flagged by a different rule instead

D1 A deprecated role

directory was deprecated in ARIA 1.2, but it's still a valid role, so this rule passes it.

Staff list
<div role="directory">Staff list</div>

Expected result: flagged by aria-deprecated-role instead

Template routing: aria-deprecated-role. Routes to: NEW-32.

D2 A deprecated DPUB role

Smith, J. (2024). Accessible forms.
<div role="doc-biblioentry">Smith, J. (2024). Accessible forms.</div>

Expected result: flagged by aria-deprecated-role instead

This also fails aria-allowed-role.

Template routing: aria-deprecated-role routes to NEW-32, and aria-allowed-role routes to NEW-31.

Changes after interaction

Axe only sees the page as it is when you run it. These pass on page load. Activate each button, then run axe again.

F1 A script sets the role from an empty variable

The script means to turn the div into a tab, but the variable is never set, so the role becomes the text undefined.

Delivery
<button type="button" id="f1-button">Make it a tab</button>
<div id="f1-target">Delivery</div>

On load: pass. After pressing: fail

After pressing, the check is invalidrole, so it routes to NEW-30.
