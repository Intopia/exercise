Testing the axe rule aria-allowed-role

Test cases for the axe-core rule aria-allowed-role (axe-core 4.14). Each HTML element only allows some ARIA roles, as set out in ARIA in HTML. The rule checks that the role attribute uses a role the element allows. For example, a heading can be a tab, but not a button.

Some things to know about this rule:

  • It's a best practice rule, not a WCAG requirement.
  • Giving an element its own role again, like <button role="button">, is allowed.
  • If the element is hidden, a role that isn't allowed is needs review, not a fail, because it may never be shown.
  • In a list of roles, every valid role must be allowed on the element.

Each case also shows the axe message key and which Intopia issue template the result would go to under the current assembly rules. Results on this page were checked in Chrome.

axe-core results: See the HTML report from running axe-core 4.14.0 over this page.

Every example is live in the page, so you can run the axe extension straight over it. The expected results were checked by running axe-core 4.14.1 over this page. Look in both the axe issues list and the needs review list.

Roles the element doesn't allow

These fail with "ARIA role ... is not allowed for given element".

A1 A heading turned into a button

A very common pattern for accordions. Put a <button> inside the heading instead.

Delivery and returns

<h2 role="button" tabindex="0">Delivery and returns</h2>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A2 A button turned into a heading

<button type="button" role="heading" aria-level="2">Our team</button>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A3 A list turned into navigation

Wrap the list in a <nav> instead.

  • Home
<ul role="navigation">
  <li><a href="#a3">Home</a></li>
</ul>

Expected result: fail

This also fails the listitem rule, because the <li> is no longer inside a list.

Template routing: Message key: none. Routes to: NEW-31.

A4 A text field turned into a button

<input type="text" role="button" aria-label="Choose a date">

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A5 A label turned into a button

Labels don't allow any role.

<label role="button" tabindex="0">Upload a file</label>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A6 A main landmark given another role

This week's offers.
<main role="region" aria-label="Offers">This week's offers.</main>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A7 A heading in capitals

Role names aren't case sensitive, so this is the same as A1.

Show more

<h2 role="BUTTON" tabindex="0">Show more</h2>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A8 A checkbox turned into a button, without aria-pressed

A checkbox can only be a button if it's a toggle button, with aria-pressed. Compare with E4.

<input type="checkbox" role="button" aria-label="Bold">

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

A9 role="none" on a label

<label role="none">Name</label>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31.

Presentational roles on things people use

These fail this rule and presentation-role-conflict, because the element can still receive focus.

B1 role="presentation" on a link

Terms 
<a href="#b1" role="presentation">Terms</a>

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31. The presentation-role-conflict result routes to NEW-35, which wasn't in this review.

B2 A decorative image turned into a button

An image with alt="" only allows none or presentation.

<img src="data:image/gif;base64,R0lGODlhAQABAAAAACw=" alt="" role="button" tabindex="0" width="20" height="20">

Expected result: fail

Template routing: Message key: none. Routes to: NEW-31. The presentation-role-conflict result routes to NEW-35, which wasn't in this review.

Role lists

C1 Two valid roles, one not allowed

Browsers would use tab, which a heading allows. But axe checks every valid role in the list, and a heading doesn't allow button.

Specifications

<h2 role="tab button">Specifications</h2>

Expected result: fail

Arguably a false positive, since the role browsers use is allowed.

Template routing: Message key: none. Routes to: NEW-31.

C2 An invalid role, then an allowed one

The invalid role is skipped, and tab is allowed on a heading.

Reviews

<h2 role="buton tab">Reviews</h2>

Expected result: pass (valid)

aria-roles doesn't flag the typo either, because one of the roles is valid.

Hidden elements

A role that isn't allowed on a hidden element is needs review, with the message "must be removed when the element is made visible".

D1 Hidden with the hidden attribute

Hidden question

<h2 role="button" tabindex="0" hidden>Hidden question</h2>

Expected result: needs review

Template routing: Needs review, message key: none. Routes to: NEW-31.

D2 Hidden with display: none

Hidden answer

<h2 role="button" tabindex="0" style="display: none;">Hidden answer</h2>

Expected result: needs review

Template routing: Needs review, message key: none. Routes to: NEW-31.

D3 Hidden with aria-hidden

Hidden heading

<h2 role="button" tabindex="0" aria-hidden="true">Hidden heading</h2>

Expected result: needs review

This also fails aria-hidden-focus, because it can still be reached with the Tab key.

Template routing: Needs review, message key: none. Routes to: NEW-31. The aria-hidden-focus result routes to NEW-48.

D4 A hidden input

A hidden input is never shown, so this will stay needs review.

<input type="hidden" role="button" value="1">

Expected result: needs review

Template routing: Needs review, message key: none. Routes to: NEW-31.

Allowed, but it doesn't behave that way

This rule checks the role is allowed, not that the element behaves like it. Nothing in axe flags these.

E1 A link turned into a button

Allowed, but a link only responds to Enter. A button should also respond to the Space bar, so this needs a script.

Add to cart 
<a href="#e1" role="button">Add to cart</a>

Expected result: passes, but it's broken (check manually)

Template routing: No result, so nothing to route.

E2 A paragraph turned into a button

A paragraph allows any role. With no script, it can be reached with Tab, but nothing happens when you press Enter or Space.

Read more

<p role="button" tabindex="0">Read more</p>

Expected result: passes, but it's broken (check manually)

Template routing: No result, so nothing to route.

Ways to pass

Control cases.

F2 A checkbox turned into a switch

<label><input type="checkbox" role="switch"> Dark mode</label>

Expected result: pass (valid)

F3 A div turned into a button

A <div> allows any role.

Apply
<div role="button" tabindex="0">Apply</div>

Expected result: pass (valid)

F4 A checkbox turned into a toggle button

With aria-pressed, this is allowed. Compare with A8.

<input type="checkbox" role="button" aria-pressed="false" aria-label="Italic">

Expected result: pass (valid)

F5 A layout table

NameAlex
<table role="presentation">
  <tr><td>Name</td><td>Alex</td></tr>
</table>

Expected result: pass (valid)

F6 role="list" on a list

Often added so Safari still reads a list with its bullets removed.

  • Fruit
<ul role="list" style="list-style: none;">
  <li>Fruit</li>
</ul>

Expected result: pass (valid)

Changes after interaction

Axe only sees the page as it is when you run it. These pass on page load. Activate each button, then run axe again.

G1 An accordion heading that's shown later

On load, the heading is hidden, so axe only reports needs review. Show it, and the same role becomes a fail.

How long does delivery take?

<button type="button" id="g1-button">Show the FAQ</button>
<h2 role="button" tabindex="0" id="g1-heading" hidden>How long does delivery take?</h2>

On load: needs review. After showing: fail

After showing, it routes to NEW-31 as a fail rather than needs review.
