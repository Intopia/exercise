Different types of accessibility testing tools

Here is a wide range of tools and approaches that help teams identify and address accessibility issues, from design and content through to development, testing and automation.

No single tool or type of testing finds every accessibility issue. Most teams combine automated tools with manual testing and assistive technology testing.

Tools are listed alphabetically within each category. Inclusion does not imply endorsement by Intopia. All external links open in a new tab.

Automated accessibility platforms

These are large-scale tools that allow multiple users to run checks across a whole website.

Good for: scanning many pages at once, monitoring sites over time, and reporting on issues across teams.

Limitations: automated checks detect only a portion of accessibility issues. They cannot judge whether content is meaningful, such as whether alt text accurately describes an image. Results still need manual review.

Developer and CI tools

These tools let developers run automated accessibility checks inside their own code, unit tests and build pipelines.

Good for: catching issues early and preventing regressions before code is deployed.

Limitations: they share the limits of all automated testing, and require developer setup and maintenance.

Browser extensions

These tools allow us to check aspects of accessibility directly in the browser.

Good for: quick checks of a single page, highlighting issues visually on the page, and learning about common issues.

Limitations: they test one page or state at a time. Different extensions use different rules, so results may vary between tools.

Built-in browser tools

These tools come built into browser developer tools, so nothing needs to be installed.

Good for: inspecting the accessibility tree, and checking the names, roles and states that are passed to assistive technologies.

Limitations: they show what the browser exposes, not how a specific screen reader will announce it. Some technical knowledge is needed to interpret results.

Bookmarklets

Simple tests that allow us to test individual accessibility issues.

Good for: highlighting one specific feature on a page, such as headings, focus order or alt text. They work in most browsers and need no installation.

Limitations: they show what is on the page but do not decide whether it is correct. Some websites block bookmarklets from running.

Colour contrast tools

These tools are focused on testing colour contrast.

Good for: precise contrast ratio checks, including on design files before anything is built.

Limitations: most test one colour pair at a time. Text over images, gradients and transparent colours can be difficult to measure accurately.

Colour contrast tools

Content testing tools

These tools test the readability and clarity of written content.

Good for: spotting long sentences, complex words and passive voice, and estimating reading level.

Limitations: readability formulas measure word and sentence length, not real understanding. Most are designed for English. They do not replace testing content with real users.

Automated mobile tools

These tools provide automated testing for accessibility on mobile devices.

Good for: checking native apps for issues like missing labels, small touch targets and low contrast.

Limitations: like web automated tools, they find only a portion of issues. Apps should also be tested with VoiceOver and TalkBack.

Keyboard testing

Testing with only a keyboard requires no tools and can be done in any browser.

Good for: checking that everything can be reached and used without a mouse, that focus order is logical, that focus is always visible, and that there are no keyboard traps.

Limitations: it does not tell you what a screen reader announces.

Keyboard testing
Tool Platform Cost Typical users
Keyboard-only navigation (Tab, Shift+Tab, Enter, Space, arrow keys, Escape) Any browser Built in Everyone

Screen readers

These are the most commonly used screen readers across desktop and mobile devices.

Good for: confirming that headings, labels, roles and states actually work for screen reader users, especially for complex components such as menus, dialogs and forms.

Limitations: there is a learning curve, and testing takes longer. Behaviour can differ between screen reader and browser combinations, so testing with one screen reader does not cover them all.

Screen readers
Tool Platform Cost Typical users
JAWS - Job Access With Speech Windows Paid Testers, developers
NVDA - NonVisual Desktop Access Windows Free Testers, developers
TalkBack Android Built in Testers, developers

Screen magnification and low vision tools

These tools enlarge content or change how it is displayed.

Good for: checking that content reflows, text resizes without loss of content, and nothing is cut off or overlaps when zoomed.

Limitations: they show the experience of zooming, but low vision needs vary widely. Results should be combined with other testing.

Languages and formats for describing accessibility

These are not testing tools. They are structured ways of writing down accessibility requirements, test cases, test rules or results, so that everyone on a team can read and agree on them. Many can be connected to the tools above to run as automated tests.

Good for: turning accessibility requirements into clear, shared acceptance criteria. They help designers, product owners, testers and developers describe the same behaviour in the same way.

Limitations: a test is only as good as what it describes. Writing good scenarios still needs accessibility knowledge, and automated runs still need to be checked with assistive technology.

Languages and formats for describing accessibility
Language What it describes Maintained by Typical users
ACT Rules Format (Accessibility Conformance Testing) Test rules: a standard format for writing accessibility test rules, so different tools and testers get consistent results W3C Tool makers, accessibility specialists
EARL (Evaluation and Report Language) Test results: a machine-readable format for recording and sharing accessibility test results W3C Tool makers, developers
Gherkin Behaviour scenarios: plain-language "Given, When, Then" steps that can describe accessible behaviour and be run by frameworks such as Cucumber Cucumber open source project Product owners, testers, developers
UCDL (Use Case Definition Language) Accessibility use cases: user tasks written as readable steps, with elements identified by role and accessible name, that can be run as automated browser tests AFixt Testers, product owners, developers
