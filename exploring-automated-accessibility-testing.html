Exploring automated accessibility testing

Published: 22 October 2026 | Author: Russ Weakley

Automated accessibility testing can help teams find accessibility issues, check how components behave, and prevent problems from being introduced during development.

This series of six articles explores how tools like axe-core and Playwright work, what they can and can't test, and how they can be used together. It starts with the basic concepts, then gradually builds towards more advanced testing techniques.

Along the way, you'll see that there's nothing magical about these tools. You can understand how they work, control what they test, and decide how to use the results.

The series is for:

  • accessibility professionals who want to understand how development teams test for accessibility
  • developers and testers who are new to automated accessibility testing
  • product owners and team leads who want to know what automated accessibility testing can and can’t do (article 1 is a good place to start)

You don't need any coding experience to start. Every step is explained in plain language.

1. Understanding axe-core and Playwright

An introduction to the two tools used in this series, with nothing to install and no code to run. Learn what each tool does, what it can and can't test, and how they can work together to support accessibility testing.

Why this matters: Before getting into code, it's useful to understand the different roles these tools play. axe-core scans a page for accessibility issues that can be detected automatically. Playwright controls a browser and tests how a website behaves, including its accessibility. They do different jobs, and using them together lets teams test more than either tool can on its own.

2. Running axe-core in the browser console

Start using axe-core without installing any software. Run accessibility checks directly in your browser's developer console, explore the results, and learn how axe-core works behind the scenes.

Why this matters: Many people first meet axe-core through a browser extension, where the underlying processes are hidden. Running it in the console is not how most teams would test websites in practice, but it's a simple way to look under the hood. You can see the results axe-core produces and experiment with how those results are displayed and filtered, without needing to build an application or set up a development environment.

3. Setting up Node.js

Prepare your computer for more advanced testing. Install Node.js and the tools needed to run axe-core outside the browser console and begin automating accessibility checks.

Why this matters: Running tests in the browser console is useful for learning, but you have to open a browser and run commands by hand. Node.js lets JavaScript tools like axe-core and Playwright run outside the browser, straight from your computer's command line. This means you can start running repeatable tests and creating scripts to automate the process.

4. Running axe-core from the command line

Move beyond testing one page at a time. Run axe-core from the command line, test multiple pages, save results, generate reports, and explore how accessibility failures can be used to stop automated processes.

Why this matters: Rather than manually opening pages and running checks, you can automate the process with simple commands. You also gain control over how results are saved and reported. Most importantly, tests can be set up to return a failure status when accessibility issues are found, allowing development teams to use them in automated build and release processes.

5. Running axe-core with a Playwright script

Take greater control of your accessibility testing by combining axe-core with Playwright. Learn how to write scripts, customise which issues cause tests to fail, generate reports, and automatically rerun tests as you make changes.

Why this matters: The command line tool can report a failure when accessibility issues are found, but it fails on any violation, even a minor one. By writing your own script, you decide what counts as a failure, how results are reported, and when the checks run. This approach is closer to how development teams typically use axe-core in practice.

6. Accessibility testing with Playwright

Move beyond the issues axe-core can detect automatically. Explore six practical examples of testing accessibility behaviour with Playwright, including keyboard interactions, component states, focus management and form errors.

Why this matters: Automated accessibility scanners can only detect certain types of issues. They cannot reliably determine whether every interaction behaves as expected. Playwright allows you to write tests for specific behaviours, such as whether a dialog receives focus when opened or whether a disclosure updates its expanded state. These tests can help teams check expected accessibility behaviour and prevent regressions as their products change.

Where to start

If you're new to automated accessibility testing, start with the first article and work through the series in order. Each article introduces new concepts and techniques.

If you're already comfortable with axe-core or Playwright, you can jump directly to the topics that interest you. Just note that articles 4 and 5 rely on the setup covered in article 3.

Automated accessibility testing is only one part of a wider accessibility testing process. These tools can help find issues and prevent regressions, but they don't replace manual testing or testing with people with disability.
