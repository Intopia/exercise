Testing the axe rule aria-braille-equivalent

Test cases for the axe-core rule aria-braille-equivalent (axe-core 4.14). ARIA 1.3 adds two attributes that change what a braille display shows, without changing what a screen reader says:

  • aria-braillelabel: a shorter braille version of the element's accessible name.
  • aria-brailleroledescription: a shorter braille version of aria-roledescription.

Both are meant to replace something that's already there. The rule checks that it is: the element must have an accessible name for aria-braillelabel, and a non-empty aria-roledescription for aria-brailleroledescription. It only runs on elements that have one of the two attributes.

This rule never fails. It's set up with reviewOnFail, so every problem it finds is reported as needs review, not as a violation. That has a big effect on the template routing:

  • NEW-33 and NEW-42 are both mapped to violations, which this rule never produces. Neither template can ever be used.
  • The map sends a braille-label-equivalent needs review to "No template", on the basis that it only happens when axe can't work out the name. In practice it's what every missing name looks like, so every braille label problem is dropped.
  • A braille-roledescription-equivalent needs review has no row at all.

The "Unable to compute accessible text" message the map is describing only appears if axe hits an error while working out the name. None of these cases produce it.

axe-core results: See the HTML report from running axe-core 4.14.0 over this page.

Every example is live in the page, so you can run the axe extension straight over it. The expected results were checked by running axe-core 4.14.1 over this page. Look in both the axe issues list and the needs review list.

Braille label with no accessible name

These are needs review, with the message "aria-braillelabel is used on an element with no accessible text". The check sets no message key and no data. Most are also caught by a naming rule such as button-name, which is where the real problem is.

A1 Icon button with a braille label

The braille display would show "del", but a screen reader has nothing to say.

<button type="button" aria-braillelabel="del">
  <svg width="16" height="16" viewBox="0 0 16 16" aria-hidden="true"><circle cx="8" cy="8" r="6"></circle></svg>
</button>

Expected result: needs review

Also fails button-name.

Template routing: Needs review. Check: braille-label-equivalent, message key: none. Routes to: no template today, because the map sends every braille-label-equivalent needs review to "No template". Should be NEW-33.

Not caught by this rule

D1 Braille label that says something else

The rule only checks that a name exists, not that the braille label matches it. A screen reader says "Delete account" and the braille display shows "ok".

<button type="button" aria-braillelabel="ok">Delete account</button>

Expected result: passes, but it's broken (check manually)

Template routing: No result, so nothing to route.

D2 Braille label on a span with text

Axe counts the text as the span's accessible name. Browsers don't, because a plain <span> can't be named, so Chrome shows it with no name and the braille label has nothing to replace.

New 
<span aria-braillelabel="nw">New</span>

Expected result: passes, but it's broken (check manually)

Template routing: No result, so nothing to route.

D3 Role description on a div with no role

aria-roledescription isn't supported on an element with no role, so Chrome ignores it, and the braille version goes with it. Axe's aria-roledescription rule would catch this, but it's off by default.

Slide 6 
<div aria-roledescription="slide" aria-brailleroledescription="sld">
  Slide 6
</div>

Expected result: passes, but it's broken (check manually)

Template routing: No result, so nothing to route.

D4 Misspelled aria-braille-label

Axe doesn't know the attribute, so this rule doesn't run. aria-valid-attr catches the spelling.

<button type="button" aria-braille-label="del">Delete</button>

Expected result: flagged by aria-valid-attr instead

Template routing: Routes to: NEW-26, not NEW-33.

Changes after interaction

Axe only sees the page as it is when you run it. These pass on page load. Activate each button, then run axe again.

E1 Button text replaced by an icon

On load, the button has text. The button below swaps the text for an icon, as a responsive script might, but leaves the braille label behind.

<button type="button" id="e1-target" aria-braillelabel="sv">Save</button>
<button type="button" id="e1-shrink">Switch to icon</button>

On load: pass. After clicking: needs review

After clicking, the button has no name, so it also fails button-name.

E2 Role description removed

On load, the slide has both role descriptions. The button removes aria-roledescription but forgets the braille one.

Summary 
<div role="article" id="e2-slide" aria-label="Slide 7" aria-roledescription="slide" aria-brailleroledescription="sld">
  Summary
</div>
<button type="button" id="e2-button">Remove role description</button>

On load: pass. After clicking: needs review

After clicking, the message key is noRoleDescription.
